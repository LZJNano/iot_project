# 4. 设备端软件实现

在上一章节中,我们已经完成了所有环境的配置:VMware 虚拟机桥接到有线网卡,Ubuntu 12.04 虚拟机提供 NFS 服务与 Mosquitto broker,实验箱从 NFS 挂载根文件系统并启动嵌入式 Linux。本章正式进入开发环节,详细描述实验箱上运行的 `mqtt_iot` 客户端程序的实现。

设备端程序的总体目标是:**接收 broker 转发的控制命令,操作对应的硬件外设;同时周期性地把传感器数据 publish 到 broker,供上位机订阅消费**。这是一个典型的物联网终端节点角色——既是数据生产者(传感器上报),也是指令执行者(控制外设)。

## 4.1 设备端软件总体架构

### 4.1.1 设计目标与约束

在动手写代码之前,我们梳理了几个关键的设计约束:

- **资源受限**:实验箱是 ARM Cortex-A53 处理器,256~512 MB 内存,Linux 用户态程序应保持精简,避免引入大型运行时
- **多外设并发**:LED、LCD、DHT11、舵机、蜂鸣器等 5 类外设需要并发工作,且对外通信(MQTT)与传感器采集不能互相阻塞
- **网络不稳定**:MQTT 长连接可能因 VM 端 broker 重启、网线松动等原因断开,需要自动重连且不丢数据语义(温湿度可丢,控制命令不可丢)
- **运行环境特殊**:根文件系统是 NFS 挂载的,`/dev` 是空目录(没有 devtmpfs),需要程序自给自足解决设备节点问题

基于这些约束,我们选择了**生产者—消费者 + 事件驱动**的经典架构,以**三线程**协作完成所有工作。

### 4.1.2 模块划分

整个 `mqtt_iot` 程序按职责拆分为 6 个源文件,每个文件对应一个明确的模块:

```
mqtt_iot/
├── main.c          # 入口、信号处理、外设初始化、命令分发
├── mqtt_client.c   # libmosquitto 0.15 封装(连接/订阅/发布/回调)
├── dht11.c         # DHT11 温湿度传感器
├── led.c           # 4 颗 LED 灯
├── lcd.c           # LCD 全屏颜色填充
├── servo.c         # 舵机角度控制
└── beep.c          # 蜂鸣器(预留,驱动未装)
```

**模块化设计的几个考量**:
- **每个外设独立成文件**:便于单独编译、单独调试、单独替换(例如要换一种传感器只需重写对应 .c)
- **统一的接口约定**:每个外设模块都暴露 `xxx_init()`、`xxx_release()`、`xxx_set_xxx()` 三个函数,主程序不必关心每个外设的具体实现细节
- **MQTT 通信与设备操作解耦**:`mqtt_client.c` 只负责 broker 通信,`main.c` 的 `on_ctrl_message()` 负责把字符串命令分发到对应的外设模块,职责清晰

### 4.1.3 三线程模型

`mqtt_iot` 启动后有 3 个线程同时运行,各司其职:

| 线程 | 职责 | 关键调用 |
|------|------|----------|
| **主线程** | 启动所有模块、等待信号、退出时清理资源 | `mqtt_client_start()`、创建 DHT11 线程、`while(!should_exit) sleep(1)` |
| **MQTT loop 线程**(pthread) | 唯一与网络打交道的线程,100 ms 轮询一次,处理收发与心跳 | `mosquitto_loop(mosq, 100)` 循环 |
| **DHT11 数据线程**(pthread) | 每 5 s 读一次传感器,push 到 broker | `read /dev/dht11` + `mqtt_client_publish` |

**为什么需要 3 个线程?**

最直觉的方案是单线程:在主循环里同时做"读传感器"和"处理 MQTT"。但这有两个问题:
1. **互相阻塞**:`read /dev/dht11` 阻塞约 100~200 ms,这段时间内无法处理 MQTT 消息,导致控制命令响应延迟
2. **周期不匹配**:DHT11 采样周期是 5 s,MQTT 轮询周期是 100 ms,放一个循环里很难协调

引入多线程后,每个线程按自己的节奏运行,互不干扰。`mosquitto_publish()` 是线程安全的(库内部有锁),DHT11 线程可以直接调用而无需额外的同步机制;DHT11 线程与主线程之间也不共享内存,只通过 broker 间接通信,因此完全无需加锁。

**为什么是 3 个而不是 2 个?**

理论上"loop 线程 + DHT11 线程"就够了,主线程把活干完就退出。但我们希望程序能响应 Ctrl+C 优雅退出,所以主线程保留,挂一个 `while (!should_exit) sleep(1)` 的简单循环,接住 SIGINT/SIGTERM 后设置退出标志,各线程在下一轮迭代中检测到标志后自行清理退出。

**libmosquitto 0.15 的特殊性**:这个版本(2010 年发布)没有 `mosquitto_loop_start()` 这种"自动起线程"函数,所以我们自己用 pthread 跑 `mosquitto_loop()`。这是与新版最大的差异,也是代码中那个显式 pthread 线程存在的原因。

### 4.1.4 启动流程

`main.c` 的执行流程如下:

```c
// main.c 精简后的 main()
int main(int argc, char *argv[]) {
    // 1. 命令行参数覆盖 broker IP,便于在不同网络环境测试
    if (argc >= 2) mqtt_client_set_host(argv[1]);

    // 2. 注册信号处理:优雅退出 + 忽略 SIGPIPE(网络断时 write 可能触发)
    signal(SIGINT, on_signal);
    signal(SIGTERM, on_signal);
    signal(SIGPIPE, SIG_IGN);

    // 3. 外设初始化 — 全部失败不退出,只记日志
    led_init(); lcd_init(); dht11_init();
    servo_init(); beep_init();

    // 4. MQTT 启动 — 创建 mosq 实例、注册回调、连接 broker
    mqtt_client_start();

    // 5. 创建 DHT11 数据采集线程
    pthread_create(&dht11_tid, NULL, dht11_thread_fn, NULL);

    // 6. 主线程等待退出信号
    while (!g_should_exit) sleep(1);

    // 7. 清理(对称释放,避免 fd 泄漏)
    pthread_join(dht11_tid, NULL);
    mqtt_client_stop();
    led_release(); lcd_release();
    dht11_release(); beep_release(); servo_release();
    return 0;
}
```

**几个值得注意的设计**:
- **所有外设 init 在 MQTT 之前**:确保本地资源就绪,再开始网络通信
- **pthread_join 等待 DHT11 线程结束**:保证采集线程正常退出(它每 5 s 检查一次 `g_should_exit`),不会留下僵尸线程
- **init/release 严格对称**:每个 `xxx_init()` 都有对应的 `xxx_release()`,关闭 fd、unmap 内存、free 资源,保证进程退出时不泄漏

## 4.2 设备控制实现

### 4.2.1 DHT11 温湿度采集

**硬件背景**:DHT11 是一款数字温湿度传感器,使用单总线协议与 MCU 通信。一次完整的数据传输包括:主机拉低 20 ms 启动信号 → 传感器拉低 80 µs 响应 → 传感器拉高 80 µs 准备 → 40 bit 数据(8 bit 湿度整数 + 8 bit 湿度小数 + 8 bit 温度整数 + 8 bit 温度小数 + 8 bit 校验和),每个 bit 由 50 µs 低电平 + 26~28 µs(数据 0)或 70 µs(数据 1)高电平表示。

在我们的设计中,**单总线协议时序由内核空间的 DHT11 驱动完成**(GPIOD25 引脚,看驱动源码),用户态程序只需 `open()` 设备节点 + `read()` 4 字节即可获得结果。这样设计的好处是:
- **时序精度有保障**:内核态跑中断或工作队列,不会被用户态进程调度影响
- **用户态代码简洁**:`read()` 阻塞等待驱动完成一次完整协议,然后返回数据
- **多进程可共享**:字符设备允许多个进程同时打开

**设备节点**:`/dev/dht11`,主设备号 804,次设备号 0。这两个数字是华清远见出厂驱动代码里写死的,我们必须照搬。

**关键技术点**:

1. **自动 mknod**——实验箱的"特殊问题":实验箱的根文件系统是 NFS 挂载的(`/source/rootfs` 从 VM 导出),而 NFS 根的 `/dev` 目录在编译 rootfs 时就是空的,内核启动后也不会自动填充(因为没有 devtmpfs 也没有 mdev)。所以 `open("/dev/dht11")` 第一次会失败,errno 是 ENOENT。

   我们的解决方法是:在程序里检测到 `open` 失败时,主动调用 `mknod(2)` 系统调用创建设备节点,然后重试:
   ```c
   g_fd = open(DHT11_DEV_PATH, O_RDWR);
   if (g_fd < 0) {
       LOG_W("open failed, try mknod and retry");
       try_mknod();                // stat 检查 → mknod 创建
       g_fd = open(DHT11_DEV_PATH, O_RDWR);   // 再开
   }
   ```
   这种"自给自足"的写法对嵌入式环境很关键——如果依赖外部脚本 `mknod /dev/dht11 c 804 0`,每次重启都要手动执行,容易遗忘。

2. **驱动返回的字节序**——另一个隐藏坑:6818B 出厂的 DHT11 驱动 `read()` 实现是:
   ```c
   copy_to_user(buf, dht11->data + 1, count);  // 返回 data[1..4],跳过 data[0]
   ```
   也就是说返回的是 `data[1..4]`,对应:
   ```
   buf[0] = 湿度小数(data[1])
   buf[1] = 温度整数(data[2])
   buf[2] = 温度小数(data[3])
   buf[3] = 校验和(data[4])
   ```
   而 `data[0] = 湿度整数` 被驱动跳过了(可能是驱动作者认为整数部分最常用,小数可有可无,但实际反过来)。**这个细节只看代码注释("buf[0]=温度小数")会理解错**,我们反复对照驱动源码 `copy_to_user(buf, data+1, 4)` 这行才确认。

3. **阻塞读**:`read()` 阻塞约 100~200 ms,这段时间驱动在等 DHT11 传感器的时序响应(一次完整协议约 100 ms,加上校验失败重试可能更久)。5 s 采样周期下,200 ms 阻塞完全可接受。

4. **JSON 数据格式**:温湿度数据 publish 到 `s5p6818/env/data` 主题,采用 JSON 格式:
   ```json
   {"hum":60,"temperature":25}
   ```
   JSON 的优势是:自描述、跨语言兼容、上位机(无论 Python/Java/QT)都能直接解析。本项目虽然数据简单(只 2 个字段),但用 JSON 是为以后扩展(比如加气压、光照)留下余地。

### 4.2.2 LED 灯珠控制

**硬件接口**:`/sys/class/leds/led{1..4}/brightness`(sysfs 伪文件)

**什么是 sysfs**:Linux 内核把很多设备信息以文件系统的形式暴露到用户态,挂在 `/sys/` 下,这就是 sysfs。对于 LED 这种简单的"开关"型设备,内核为每个 LED 在 `/sys/class/leds/ledN/` 下创建了一组属性文件,其中 `brightness` 接受写入"0"或"1"来控制开关。这种"一切皆文件"的接口让用户态控制硬件不需要写特殊的 ioctl,直接 `write()` 即可。

**关键技术点**:

1. **基本的 sysfs 控制方式**:打开 brightness 节点,`write(fd, "0", 1)` 或 `write(fd, "1", 1)` 即可控制。在普通开发板上,`0` 灭,`1` 亮。

2. **FS6818B 板子的反相 bug**:实测发现 FS6818B 实验箱的 LED 逻辑是反的——写 `"0"` 灯亮,写 `"1"` 灯灭。这点用户手册上没有说明,只能通过实测发现。我们猜测是硬件原理图里 LED 的供电通路设计导致的(可能 LED 的阳极接到 GPIO,阴极接到 VCC,这样 GPIO 高电平两端电压相等,LED 不导通;GPIO 低电平两端有压差,LED 导通发光)。代码里做了对调:
   ```c
   const char *v = on ? "0" : "1";   // 板子反相:on=1 时写 0 才亮
   ```
   **这个 bug 的发现过程值得记录**:第一天演示时,实验箱不响应 LED 控制,反复检查 broker 配置、MQTT 主题、代码逻辑,最后用 `cat /sys/class/leds/led1/brightness` 看实际值,再手动 `echo 0 > brightness` 测试,才发现板子逻辑反了。这种"硬件反直觉"的问题在没有完整数据手册时只能靠实验发现。

3. **fd 缓存**:`led_init()` 在程序启动时一次性打开 4 个 LED 的 sysfs 节点,fd 存入 `g_led_fd[]` 数组。后续 `led_set_one()` 只做 `write()` 系统调用,不重新 `open()`。这样设计虽然在小项目里节省的时间可以忽略不计,但体现了"避免系统调用浪费"的工程习惯——如果将来扩展到几十个 LED,这种优化就很有意义了。

4. **优雅降级**:任一 LED 的 sysfs 节点打开失败(比如设备树里没定义某个 LED)都不影响其他 LED,程序整体不退出。这与"任一外设失败不影响主程序"的设计原则一致,体现了"系统级鲁棒性"的工程思维。

### 4.2.3 LCD 显示屏控制

**硬件接口**:`/dev/fb0`(Linux framebuffer 设备,板载 LCD 1024×600,32 bpp)

**什么是 framebuffer**:Linux 提供的显示子系统抽象,把显卡(或 LCD 控制器)的显存映射成一个设备文件 `/dev/fb0`。应用程序打开这个文件,通过 `ioctl` 获取屏幕参数(分辨率、色深、每行字节数等),然后用 `mmap` 把显存映射到用户态虚拟地址空间,就可以像访问普通内存一样读写像素——`*ptr = 0xFF0000` 就把那个像素设为红色。这种"一切皆文件 + mmap"的设计让应用程序可以用高级语言控制屏幕,而不必在内核态写驱动。

**关键技术点**:

1. **mmap 显存映射**:这是 framebuffer 编程的核心技巧。直接 `write(fd, ...)` 系统调用只能写少量数据,刷全屏要写 2.4 MB,效率很低。用 mmap 把显存映射成普通内存指针后,`g_fbp[y * line_length + x * 4] = color` 就能改屏幕,内核会负责把改动同步到硬件。
   ```c
   g_fbp = mmap(0, g_screensize, PROT_READ|PROT_WRITE, MAP_SHARED, g_fbfd, 0);
   ```
   `MAP_SHARED` 表示这块内存是共享的(进程和内核/硬件共享),`PROT_READ|PROT_WRITE` 表明要读写权限。

2. **通过 ioctl 获取屏幕参数**:打开 fb0 后,需要知道屏幕多大、每像素几字节,才能正确读写。通过两个 ioctl:
   - `FBIOGET_FSCREENINFO` 取得 `line_length`(每行字节数,**可能大于** `xres * bpp/8`,因为硬件可能要求每行对齐到 32 字节或 64 字节)
   - `FBIOGET_VSCREENINFO` 取得 `xres/yres/bits_per_pixel`
   这两个结构体是 framebuffer 编程的标准接口,所有 Linux 平台都一样。

3. **6 种颜色填充**:本项目只做"全屏填一种颜色"的简单功能,不画图、不画线、不写字。6 种颜色用 32 位 ARGB 宏定义:
   ```c
   #define RED   0xFFFF0000   // ARGB 格式,0xAARRGGBB
   #define GREEN 0xFF00FF00
   #define BLUE  0xFF0000FF
   #define WHITE 0xFFFFFFFF
   #define BLACK 0xFF000000
   #define YELLOW 0xFFFFFF00
   ```
   `lcd_fill_named()` 做字符串查表,`lcd_red`、`lcd_green` 等命令传进来的字符串映射到这些宏。

4. **朴素双循环填色**:
   ```c
   for (y = 0; y < yres; y++) {
       for (x = 0; x < xres; x++) {
           location = (x + xoffset) * 4 + (y + yoffset) * finfo.line_length;
           *((unsigned long *)(g_fbp + location)) = color;
       }
   }
   ```
   1024×600 = 614 400 像素,每像素 4 字节,写一遍 2.4 MB,实测填一遍约 50 ms。这个速度在我们的应用场景下完全够用(填一次全屏就 50 ms,人眼几乎察觉不到)。**生产环境可优化**:
   - 同一颜色整块用 `memset(g_fbp, color & 0xff, g_screensize)` 大幅加速(但 ARGB 每字节都是同一字节,只有 RGB 565/555 才行)
   - 32 bpp 下,可以用 DMA 或 SIMD 指令(`memset(g_fbp, color, g_screensize)` 直接写 4 字节 614400 次,C 库会用 SSE/AVX 优化)
   - Linux 内核有个 `FBIOBLIT` 接口可以直接硬件 blit,但需要驱动支持

5. **释放对称**:`lcd_release()` 先 `munmap` 再 `close`,顺序与 `lcd_init` 相反(打开先,关闭后)。这是资源管理的通用原则,避免"unmap 一个还没 close 的 fd"或"close 一个还 mmap 着的 fd"这种顺序错误。

### 4.2.4 舵机控制

**硬件接口**:`/dev/servo`(字符设备,通过 ioctl 控制)

**什么是舵机**:舵机是一种位置伺服电机,内部有电机、减速齿轮、电位器(位置反馈)、控制电路。给它一个 50 Hz 的 PWM 信号(周期 20 ms),高电平时间 500~2500 µs 对应 0°~180° 的转角。舵机内部电路会读取 PWM 高电平时间,驱动电机转到对应角度,通过电位器反馈形成闭环。

PWM 信号由 S5P6818 的 PWM 定时器 1 产生,通过 GPIOC7 输出,驱动芯片用这个 GPIO 控制舵机。

**关键技术点**:

1. **ioctl 命令宏定义**:与 LED 的 sysfs 不同,舵机这种"复杂控制"的设备通常用 ioctl 接口(可以传参数、返回状态)。命令字用宏定义在 `servo.h`:
   ```c
   #define SERVO_IOCTL_MAGIC 'S'                  // 魔数,防止命令冲突
   #define SERVO_ROTATE_0    _IO(SERVO_IOCTL_MAGIC, 0)   // 0°
   #define SERVO_ROTATE_45   _IO(SERVO_IOCTL_MAGIC, 1)   // 45°
   #define SERVO_ROTATE_90   _IO(SERVO_IOCTL_MAGIC, 2)   // 90°
   #define SERVO_ROTATE_135  _IO(SERVO_IOCTL_MAGIC, 3)   // 135°
   #define SERVO_ROTATE_180  _IO(SERVO_IOCTL_MAGIC, 4)   // 180°
   #define SERVO_SET_ANGLE   _IO(SERVO_IOCTL_MAGIC, 5)   // 任意角度
   ```
   这些宏直接拷贝自厂方驱动源码 `E:\程序源码\...\6818M4\servo_driver.c`,**保证魔数 'S' 和命令编号与驱动一致**,这是 ioctl 跨进程通信的基础——用户态和内核态必须用完全相同的 ioctl 编号,才能正确分发。

2. **5 档预设 + 任意角度**:设计了两个用户接口函数:
   - `servo_goto(slot 0~4)`:发预设命令,用于 UI 按钮直接转 5 个常用角度
   - `servo_set_angle(N)`:发任意角度命令,用于 slider 等连续控件
   对应底层:`servo_goto` 调驱动里的 `ROTATE_X` 命令(驱动内部设固定 PWM 时间),`servo_set_angle` 调 `SET_ANGLE` 命令(驱动内部按 `500us + (2500-500)/180 * angle` 线性算 PWM 时间)。

3. **PWM 原理(驱动层面)**:用户态程序不直接配 PWM 寄存器,只通过 ioctl 让驱动算。PWM 周期固定 20 ms(50 Hz),高电平时间对应角度:
   - 500 µs → 0°
   - 1000 µs → 45°
   - 1500 µs → 90°
   - 2000 µs → 135°
   - 2500 µs → 180°
   这个对应关系是舵机行业的标准(几乎所有 50 Hz 模拟舵机都是这样),由驱动代码用 `dev_work` 工作队列周期性产生 PWM。

4. **驱动依赖**:需在实验箱启动后 `insmod /lib/modules/3.4.39-farsight/extra/servo.ko`,但华清远见出厂镜像已经把舵机驱动编译进内核(built-in),所以**开箱即用**,不需要手动加载。这是华清远见"实验箱到手就能玩"的产品理念。

5. **应用层优雅降级**:如果驱动没装,`open("/dev/servo")` 失败,`g_fd` 保持 -1。后续 `servo_set_angle()` 检测 `g_fd < 0` 就 return -1,不会崩。这种设计对"实验箱硬件配置变化"的场景非常友好——比如换一台没有舵机硬件的实验箱,我们的 mqtt_iot 仍然能跑,只是舵机命令静默失效。

## 4.3 核心功能代码片段(主逻辑)

上一节描述了每个设备的实现要点,本节把**核心主逻辑**抽出来,剥离错误处理、参数检查、日志输出等细枝末节,呈现每个设备"在做什么"的最简形式。完整代码参考仓库 `src/` 目录。

### 4.3.1 DHT11 读取(主逻辑)

```c
// 1. 打开设备节点
fd = open("/dev/dht11", O_RDWR);

// 2. 读 4 字节(驱动内部完成单线协议时序,阻塞 100~200 ms)
unsigned char buf[4] = {0};
read(fd, buf, sizeof(buf));

// 3. 按驱动返回的字节序解析(buf[0]=湿度小数, buf[1]=温度整数,
//    buf[2]=温度小数, buf[3]=校验和)
int humi_dec = buf[0];
int temp_int = buf[1];
int temp_dec = buf[2];

// 4. 拼 JSON,publish 到 broker
char json[96];
snprintf(json, sizeof(json),
         "{\"hum\":%d,\"temperature\":%d}", humi_int, temp_int);
mqtt_client_publish("s5p6818/env/data", json, strlen(json), 0);
```

**主逻辑 4 步**:打开设备 → 读 4 字节 → 解析 → 发布。

### 4.3.2 LED 设置(主逻辑)

```c
// 1. 打开 4 个 LED 的 sysfs 节点(初始化时一次)
g_led_fd[0] = open("/sys/class/leds/led1/brightness", O_WRONLY);
g_led_fd[1] = open("/sys/class/leds/led2/brightness", O_WRONLY);
g_led_fd[2] = open("/sys/class/leds/led3/brightness", O_WRONLY);
g_led_fd[3] = open("/sys/class/leds/led4/brightness", O_WRONLY);

// 2. 控制单个 LED:写 "0"(亮)或 "1"(灭)到 brightness
//    (FS6818B 板子逻辑反相,故 0=亮,1=灭)
void led_set_one(int idx, int on) {
    const char *v = on ? "0" : "1";
    write(g_led_fd[idx-1], v, 1);
}

// 3. 控制所有 LED:循环调单 LED
void led_set_all(int on) {
    for (int i = 0; i < 4; i++) {
        const char *v = on ? "0" : "1";
        write(g_led_fd[i], v, 1);
    }
}
```

**主逻辑 2 步**:预开 4 个 fd → 写一个字节。

### 4.3.3 LCD 显示屏控制实现

LCD 采用 Linux framebuffer 设备(`/dev/fb0`),通过 `mmap()` 将显存映射到用户态后,可像访问普通内存一样直接对像素进行读写,无需频繁的 `write()` 系统调用。本实验箱 LCD 分辨率为 1024×600、32 bpp,我们定义了红、绿、蓝、白、黑、黄共 6 种颜色,`lcd_fill_named()` 字符串查表后调 `lcd_fill_screen()` 全屏填色。核心代码片段如下所示:

```c
int lcd_init(void) {
    g_fbfd = open(LCD_FB_PATH, O_RDWR);   // 打开 framebuffer 设备 /dev/fb0
    ioctl(g_fbfd, FBIOGET_VSCREENINFO, &g_vinfo);   // 获取屏幕参数
    g_screensize = g_vinfo.xres * g_vinfo.yres * 4;  // 计算显存大小
    g_fbp = mmap(0, g_screensize, PROT_READ | PROT_WRITE,
                 MAP_SHARED, g_fbfd, 0);             // 显存映射到用户态
}

void lcd_fill_screen(color_t color) {
    for (y = 0; y < g_vinfo.yres; y++) {              // 双循环逐像素写
        for (x = 0; x < g_vinfo.xres; x++) {
            location = (x + g_vinfo.xoffset) * 4
                     + (y + g_vinfo.yoffset) * g_finfo.line_length;
            *((unsigned long *)(g_fbp + location)) = color;
        }
    }
}
```

需要注意的是,LCD 程序假设 32 bpp 色深,其他色深(如 16 bpp)未适配,代码中对此做了断言保护。

### 4.3.4 舵机控制实现

舵机使用字符设备接口(`/dev/servo`),通过 `ioctl()` 下发控制命令。舵机角度对应 PWM 高电平时间(500 µs~2500 µs 对应 0°~180°,周期固定 20 ms),驱动由厂方实现,出厂镜像已内置。`servo_goto(slot)` 提供 5 档预设角度,`servo_set_angle(angle)` 支持 0~180° 任意角度。核心代码片段如下所示:

```c
g_fd = open(SERVO_DEV_PATH, O_RDWR);    // 打开 /dev/servo

void servo_goto(int slot) {              // 预设角度(0/45/90/135/180)
    ioctl(g_fd, _IO('S', slot), 0);     // 魔数 'S',命令编号 slot
}

void servo_set_angle(int angle) {        // 任意角度(0~180)
    if (angle < 0)   angle = 0;
    if (angle > 180) angle = 180;
    ioctl(g_fd, _IO('S', 5), angle);    // 魔数 'S',编号 5 = SET_ANGLE
}
```

需要注意的是,`ioctl` 的命令编号与魔数('S')是用户态和内核态约定的协议,必须与厂方驱动源码 `servo_driver.c` 保持完全一致,否则驱动无法识别命令。

### 4.3.5 蜂鸣器(主逻辑)

```c
// 1. 打开蜂鸣器设备节点(本项目驱动未装,此步通常失败)
int fd = open("/dev/beep", O_RDWR);

// 2. 开/关蜂鸣器
ioctl(fd, _IO('B', 0), 0);  // BEEP_ON
ioctl(fd, _IO('B', 1), 0);  // BEEP_OFF
```

**主逻辑 1 步**:开设备 + ioctl。

### 4.3.6 主程序整合(主逻辑)

```c
// 1. 启动
led_init(); lcd_init(); dht11_init(); servo_init(); beep_init();
mqtt_client_start();   // 创建 mosq,连 broker
pthread_create(&tid, NULL, dht11_thread, NULL);  // DHT11 采集线程

// 2. 主循环
while (!g_should_exit) sleep(1);

// 3. 收到控制命令(loop 线程回调 on_message → on_ctrl_message)
void on_ctrl_message(const char *cmd) {

    else if (!strcmp(cmd, "led_off")) led_set_all(0);
    else if (!strcmp(cmd, "lcd_red")) lcd_fill_named("red");
    else if (!strcmp(cmd, "servo_90")) servo_goto(2);
    else if (!strcmp(cmd, "beep_on"))  beep_on();

}
```

**主逻辑 3 步**:初始化 → 主循环 → 命令分发(字符串匹配 → 设备操作)。

## 4.4 MQTT 客户端

如前文所述,设备端软件主要包含发送传感器数据和接收控制命令两类功能,而这两类数据的流入与流出都需要一个中转机制。我们在 `mqtt_client.c` 中封装了 libmosquitto 0.15 客户端,负责与 VM 上的 broker 通信。这样,所有传感器数据从这里出去,所有控制命令从这里进来。

### 4.4.1 启动客户端

如前文所述,设备端软件启动时会启动主线程,MQTT 客户端随之启动。在启动阶段,`mqtt_client_start()` 会先初始化 mosquitto lib,随后创建客户端并注册回调,再发起 TCP 连接,最后启动后台 loop 线程。核心代码片段如下:

```c
mosquitto_lib_init();                                    // 初始化 lib
g_mosq = mosquitto_new(MQTT_CLIENT_ID, NULL);            // 创建客户端
mosquitto_connect_callback_set(g_mosq, on_connect);      // 注册回调
mosquitto_connect(g_mosq, g_host, MQTT_PORT,
                  MQTT_KEEPALIVE, MQTT_CLEAN_SESSION);    // 发起 TCP 连接
pthread_create(&tid, NULL, loop_thread_fn, NULL);        // 启后台 loop 线程
```

TCP 连接建立后,MQTT 服务由 libmosquitto 内部维护,因此所有收发直接走 `mosquitto_publish` 和 `mosquitto_loop` 库函数即可,我们不直接操作 socket。

### 4.4.2 发布采集数据

如前文所述,设备端软件在采集到温湿度数据后,需要把数据传到 broker 上。这一步由 DHT11 线程调 `mqtt_client_publish()` 完成,每 5 秒调用一次。在 publish 内部,`mosquitto_publish` 不直接发 TCP 包,而是把数据放入 libmosquitto 的内部发送队列,真正的发送由后台 loop 线程在下一轮 `mosquitto_loop(100)` 里完成,这就是生产者-消费者模型。`mosquitto_publish` 内部自带锁,线程安全,调用方无需额外加锁。核心代码片段如下:

```c
int mqtt_client_publish(const char *topic, const char *payload,
                        int payload_len, int qos) {
    return mosquitto_publish(g_mosq, NULL, topic, payload_len,
                            (const void *)payload, qos, false);
}
```

### 4.4.3 回调

如前文所述,libmosquitto 在 loop 线程里检测到网络事件时,会触发我们注册的回调函数。我们注册了 3 个回调,分别处理连接成功、收到消息、连接断开这 3 类事件。

`on_connect` 在 TCP 连接建立成功后被触发,内部完成对控制主题 `s5p6818/device/ctrl` 的订阅(QoS=1,保证至少一次到达)。订阅放在这里而不是 `mqtt_client_start()` 里,是为了让 broker 接受新连接后能自动重新订阅,避免网络抖动后丢失控制能力。

`on_message` 在收到 broker 转发的 PUBLISH 时被触发,把 payload 复制成字符串后调 `on_ctrl_message()`(在 main.c 中)分发到具体设备,核心代码片段如下:

```c
static void on_message(void *obj, const struct mosquitto_message *msg) {
    if (strcmp(msg->topic, TOPIC_DEV_CTRL) == 0) {
        char *payload = malloc(msg->payloadlen + 1);   // 二进制安全
        memcpy(payload, msg->payload, msg->payloadlen);
        payload[msg->payloadlen] = '\0';               // 加 '\0' 结尾
        on_ctrl_message(payload, msg->payloadlen);     // 调 main.c 分发器
        free(payload);
    }
}
```

`on_disconnect` 在 TCP 连接断开时被触发,仅打日志,重连由 libmosquitto 内部自动处理。

需要注意的是,MQTT 的 payload 在协议层是二进制安全的,**不保证 null 结尾**,必须 `malloc + memcpy + '\0'` 才能当 C 字符串用,否则 `strcmp` 等会越界。`on_ctrl_message` 在 main.c 中实现,根据字符串命令调用 `led_set_*` / `lcd_fill_named` / `servo_goto` 等(见 4.5)。

至此,MQTT 客户端的连接、发布、回调 3 个环节形成一个完整的闭环:**DHT11 线程**通过 `publish` 把传感器数据送出去 → broker 转发给 Controller 订阅者 → Controller 通过 `publish` 下发控制命令 → broker 转发回设备 → `on_message` 接收后交给 `on_ctrl_message` 分发到硬件。整个过程只用到 4 个 API,职责清晰。

## 4.5 命令分发协议

## 4.5 命令分发协议

`on_ctrl_message()` 在 main.c 里,负责把 MQTT 收到的字符串命令解析为具体的硬件操作:

```c
void on_ctrl_message(const char *payload, int payload_len) {
    if (!strcmp(payload, "led_on"))   { led_set_all(1); return; }
    if (!strcmp(payload, "led_off"))  { led_set_all(0); return; }
    if (!strcmp(payload, "led1_on"))  { led_set_one(1, 1); return; }
    /* ... led1_off, led2_on/off, ... */
    if (!strcmp(payload, "lcd_red"))  { lcd_fill_named("red"); return; }
    /* ... lcd_green, lcd_blue, lcd_white, lcd_black, lcd_yellow */
    if (!strcmp(payload, "servo_0"))    { servo_goto(0); return; }
    if (!strcmp(payload, "servo_45"))   { servo_goto(1); return; }
    /* ... servo_90, servo_135, servo_180 */
    if (strncmp(payload, "servo_angle", 11) == 0) {
        int a;
        if (sscanf(payload + 11, "%d", &a) == 1)
            servo_set_angle(a);
        return;
    }
    if (!strcmp(payload, "beep_on") || !strcmp(payload, "buzzer_on")) {
        beep_on(); return;
    }
    /* ... beep_off, buzzer_off */
    LOG_W("unknown command: %s", payload);
}
```

**协议设计原则**:
- **字符串协议**:不定义二进制协议、不用 JSON、不用 protobuf。理由:命令集小(约 20 个),字符串最直观,易调试(`mosquitto_pub -m led_on` 一行就能测)
- **空格分隔参数**:`servo_angle 45` 这种带参数的命令用空格分隔,比 `servo_angle=45` 或 JSON 简单
- **不响应也不报错**:`led5_on` 这种板上不存在的命令静默 return,不刷屏日志(答辩时屏幕上狂刷 WARN 不好看)
- **未知命令 WARN**:完全不认识的命令打 LOG_W,便于调试

**协议扩展性**:加新设备只需在 `on_ctrl_message` 加几行 `strcmp`,无需改其他文件。这种"开闭原则"——对扩展开放、对修改封闭——让本项目能渐进式增加功能而不破坏已有代码。

## 4.6 本章小结

设备端 `mqtt_iot` 程序的实现遵循**模块化 + 优雅降级 + 线程分离**三个原则:

1. **模块化**:每个外设一个 .c 文件,通过统一的 `init/release/set` 函数接口暴露能力。主程序不关心外设内部实现,只调接口,降低耦合
2. **优雅降级**:任一外设打开失败都不影响主程序,日志记 WARN,继续运行(例:蜂鸣器驱动未装时,`beep_on/off` 静默 return;LED 某个节点缺失时,其他 LED 仍可控)
3. **线程分离**:网络收发、传感器采集、UI/信号 三个职责分到三个线程,无共享内存,通过 MQTT 协议解耦

实验箱在本项目中作为**数据采集端**和**指令执行端**,通过标准 MQTT 协议与上位机(VirtualBox 上的 broker)解耦通信。这种解耦让本项目具有很好的扩展性:后续要加新设备(摄像头、舵机组、温湿度传感器阵列)只需添加新模块 + 改 on_ctrl_message 一行 + 在 broker 端加新的订阅者,无需重构现有代码。
