# 6. 控制端软件实现

在前面三章中,我们先后完成了实验箱端 `mqtt_iot` 客户端、VM 端 Mosquitto broker 的实现,构建了一条从传感器到 broker 的上行数据通路。本章实现系统的第三个角色——**控制端软件**(Controller),它通过订阅 broker 接收温湿度数据、通过发布控制命令操作实验箱外设,完成"人对设备"的可视化控制。

## 6.1 控制端软件总体架构

### 6.1.1 角色与定位

在前文 1.2 节我们已经明确了三方拓扑:实验箱(`mqtt_iot`)+ VM(broker)+ 控制端(Controller)。**Controller 处于整个系统的"用户侧"**,它不做任何底层硬件操作,只承担两项核心职责:一是**订阅** `s5p6818/#` 主题,接收 broker 转发的温湿度数据,显示在 UI label 上;二是**发布** 到 `s5p6818/device/ctrl` 主题,把用户点按钮产生的字符串命令(如 `led_on`、`servo_90`)推给 broker,由 broker 转发给设备。

这种"只发命令、收数据"的轻角色让 Controller 的实现可以非常简洁——它不需要写任何硬件相关代码,也不需要 libmosquitto 这类 C 客户端库,所有与 broker 的交互都被封装在一个独立的 `MqttProcess` 类里,主窗口只需要关心"按哪个按钮发什么字符串"。

### 6.1.2 技术栈选择

本系统的控制端选择 **Qt 4.8** 作为 GUI 框架,主要基于两方面的考虑。

第一,**Ubuntu 12.04 系统自带 Qt 4.8**,源码兼容,不需要安装额外依赖。我们只需要在 VM 上执行 `qmake && make` 即可编译出可执行文件,这对于需要在两台机器(VM + Windows 开发机)上分别构建的场景非常重要。

第二,在 MQTT 客户端实现上,我们没有选择 Qt 官方提供的 QtMqtt 库,而是采用 **`QProcess` 调 `mosquitto_pub` / `mosquitto_sub` 两个命令行工具** 的方案。这一选择背后的原因在 `MqttProcess.h` 的注释里写得很清楚:QtMqtt 库需要 Qt 5.6+ 和额外的 `libQt5Mqtt.so`,在 Qt 4.8 + Ubuntu 12.04 上**根本装不了**;而 `mosquitto_pub/sub` 是 broker 自带的命令行工具,任何平台都有。代价是每次发命令都要 fork 一次进程(延迟多 5~10 ms),但对于人机交互场景完全可以接受。

从部署角度看,Ubuntu 端只需要 `apt install mosquitto-clients` 即可,Windows 端从 mosquitto 官网下载安装包、把 `mosquitto_pub.exe` 和 `mosquitto_sub.exe` 加到 PATH 即可,**完全不依赖额外 C 客户端库**,这也是 .pro 工程文件里没有 `LIBS += -lmosquitto` 的原因。

### 6.1.3 模块划分

Controller 共 4 个源文件,各司其职:

| 文件                      | 行数   | 职责                                                    |
| ----------------------- | ---- | ----------------------------------------------------- |
| `main.cpp`              | 17   | QApplication 入口,设置应用名,创建并显示主窗口,进入 Qt 事件循环             |
| `MainWindow.h/.cpp`     | ~290 | 主窗口 UI 搭建,所有按钮的槽函数,MQTT 消息分发到 UI 更新                   |
| `MqttProcess.h/.cpp`    | ~110 | 用 QProcess 包装 mosquitto_pub/sub 命令行调用,屏蔽 fork+exec 细节 |
| `FarSightWidget.h/.cpp` | ~80  | 自定义控件,在右栏显示实验箱外观图,并叠加 LCD 颜色预览                        |

模块依赖是单向的:`main.cpp` 启动 `MainWindow`,`MainWindow` 持有 `MqttProcess` 实例(发命令) + `FarSightWidget` 实例(可视化),`MqttProcess` 通过信号槽与 `MainWindow` 通信。这种"一个主窗口 + 一个通信类 + 一个可视化控件"的小型结构,符合 Qt 嵌入式 GUI 应用的常见组织方式,也方便后续维护。

## 6.2 控制端软件 UI 设计

### 6.2.1 主窗口布局

主窗口采用 **左右分栏** 的经典 Qt 布局方式,通过 `QSplitter` 实现水平分割,整体效果如下图所示。

```
┌─────────────────────────┬──────────────┐
│  MQTT Broker 连接区       │              │
│  Sensor 数据显示         │   实验箱图片   │
│  LED 控制区              │   + LCD 颜色   │
│  Servo / Buzzer         │   叠加预览     │
│  LCD 颜色区              │  (FarSightWidget)│
│  Log / RX 消息          │              │
│  (~640 px 可伸缩)        │  (500 px 固定) │
└─────────────────────────┴──────────────┘
```

设计原则是"控制区在左,设备可视化在右"——左边操作,右边直观看到设备 LCD 实际会显示什么颜色,验证控制是否生效。这种布局源自工业控制面板的常见设计:操作员左侧操作仪表,右侧观察设备反馈。

窗口整体大小 960×540 像素,启动后 300 毫秒**自动调用 Connect 槽**(通过 `QTimer::singleShot`),无需用户手动点连接按钮,演示更流畅。这个细节也方便无显示器测试(xvfb 自动化场景下程序不会卡在"等用户点按钮"阶段)。

### 6.2.2 控件功能说明

UI 从上到下分 6 个 GroupBox,各控件功能如下。

**第一,MQTT Broker 连接区**(顶部,占整行)

该区域用于配置与 broker 的连接参数,包含 Host 输入框(默认 `127.0.0.1`,即本机 broker)、Port 输入框(默认 `1883`,有 `QIntValidator` 限制 1~65535)、Base Topic 输入框(默认 `s5p6818`,所有主题都以它为前缀),以及 Connect / Disconnect 两个按钮和状态 label(显示"Status: connected"或"disconnected")。Base Topic 设计为可改,是因为实际部署时可能有多台实验箱(改 `s5p6818` 为 `s5p6819` 等即可),无需改代码。

**第二,Sensor 数据显示区**

两个大字体 label,温度显示为红色 18 pt(`font-size:18pt; color:#c00`),湿度显示为蓝色 18 pt(`color:#06c`),布局为水平排列。收到 broker 转发的 `s5p6818/env/data` JSON 后,通过字符串解析(找 `"hum":N` 和 `"temperature":N` 子串)提取数据并显示,详见 6.3.3 节。

**第三,LED 控制区**(网格布局 3 行 × 6 列)

按"每行两个 LED + 一行全控"的方式排布:第 0 行 LED 1 [On][Off] + LED 2 [On][Off],第 1 行 LED 3 [On][Off] + LED 4 [On][Off],第 2 行 All [On][Off]。每个按钮通过 `setProperty("ledIdx", N)` 绑定 LED 编号,点击后从 `sender()->property("ledIdx")` 取出,生成 `led1_on`、`led2_off` 等命令字符串。

需要说明的是,源码中按钮文字"Off"对应点亮、"On"对应点灭,这是为了配合 FS6818B 板子 LED 的反相逻辑(详见 4.2.2 节)。这个细节如果不注意,演示时会出现"按 On 不亮"的反直觉现象,源码里通过文字与实际行为的对应关系做了隐式修正。

**第四,Servo / Buzzer 区**(水平布局)

一个 `QComboBox` 提供 5 个常用角度选项(0°/45°/90°/135°/180°,各带中文/英文标签如"0 deg (left)"、"90 deg (mid)"),一个"Servo Turn"按钮触发 `servo_<angle>` 命令,一个"Buzzer Beep"按钮触发 `buzzer_on` 命令。这两个功能放在同一行是因为它们都属于"非 LED 类的执行器",逻辑上属于同一类。

**第五,LCD 颜色区**(网格布局 2 行 × 3 列)

6 个色块按钮:红 / 绿 / 蓝 / 白 / 黑 / 黄,每个按钮用 `setStyleSheet` 设置**底色 = 实际 LCD 颜色**(用户点之前就知道会变什么色),并智能选择文字颜色(白/黄底用黑字,其他用白字)。点击后发 `lcd_<color>` 命令,**同时同步更新右栏 FarSightWidget 的 LCD 叠加色**——这是 Controller 的"亮点"之一,让用户立即在 GUI 上预览实验箱 LCD 会显示什么颜色,无需等真机响应。

**第六,Log / RX 消息区**(底部)

只读 `QTextEdit`,显示所有连接、收发、错误事件,每条带时间戳 `HH:mm:ss`。同时镜像输出到 stderr,方便 xvfb 无显示器测试时观察。这一段是工程师视角的"调试窗口",普通用户不一定会用,但在排查问题时至关重要。

### 6.2.3 FarSightWidget 设备可视化

右栏是自定义控件 `FarSightWidget`,固定大小 **500×406 像素**,不缩放不拉伸,展示一张实验箱的高清图(`assets/Far_Sight.png`),并在 LCD 区域(基于 Figma 量取的 228×123 矩形,top 22、left 20)叠加一个半透明矩形,颜色与右栏 LCD 按钮点击的色同步。

颜色映射严格对齐设备端 `src/lcd.h` 的 6 个宏:

| 名称 | RGB 值 | 对应设备端宏 |
|------|--------|--------------|
| red | (255, 0, 0) | `#define RED 0xFFFF0000` |
| green | (0, 255, 0) | `#define GREEN 0xFF00FF00` |
| blue | (0, 0, 255) | `#define BLUE 0xFF0000FF` |
| white | (255, 255, 255) | `#define WHITE 0xFFFFFFFF` |
| black | (0, 0, 0) | `#define BLACK 0xFF000000` |
| yellow | (255, 255, 0) | `#define YELLOW 0xFFFFFF00` |

这样设计的核心目的是**形成"所见即所得"的效果**:用户在右栏点"红"按钮,右栏 LCD 区域立即变红;100 毫秒后(网络往返 + 设备 LCD 写入),实际实验箱的 LCD 屏也会变红。两边视觉一致,操作员可以即时确认控制是否生效,无需走到实验箱前查看。

## 6.3 MQTT 通信实现

在前面第 4.4 节我们介绍了设备端 `mqtt_iot` 是如何通过 libmosquitto 库与 broker 通信的。本节我们讲控制端 Controller 是怎么跟 broker 通信的。

### 6.3.1 通信实现方式

如前文 6.1.2 所述,本系统的 Controller 没有引入 QtMqtt 等 C 客户端库,而是采用 **`QProcess` 调 `mosquitto_pub` / `mosquitto_sub` 两个命令行工具** 的方案。`QProcess` 是 Qt 自带的进程管理类,能异步启动外部程序、读写其标准输入输出,在 Qt 4.8 上无需额外依赖。

具体来说,我们的 `MqttProcess` 类对两种 MQTT 操作做了不同处理:**发布** 操作每次临时启动一个 `mosquitto_pub` 进程,发完即结束;**订阅** 操作则启动一个长生命周期的 `mosquitto_sub` 进程,持续把收到的消息按行拆出 topic 与 payload,再通过信号把 payload 送到 MainWindow。

这种"用现成工具拼凑通信能力"的设计,虽然比不上 QtMqtt 库的封装优雅,但**显著降低了项目复杂度**——任何初学者都能在 10 分钟内理解 Controller 怎么跟 broker 通信,而不必先学 QtMqtt 库的回调机制。

### 6.3.2 主题约定与命令协议

主题约定与设备端 `config.h` 完全对齐:Controller 订阅 `s5p6818/#` 主题(收温湿度),发布到 `s5p6818/device/ctrl` 主题(发控制命令)。其中收的温湿度数据是 JSON 格式 `{"hum":N,"temperature":N}`(每 5 秒一条,详见 4.2.1 节的设备端说明),发的控制命令是字符串格式。命令字符串清单如下表所述,严格对齐设备端 `on_ctrl_message` 的解析规则(详见 4.5 节):

| UI 按钮 | 发出的命令 | 设备行为 |
|---------|-----------|----------|
| LED 1~4 On | `led1_on` / `led2_on` / `led3_on` / `led4_on` | 对应 LED 亮 |
| LED 1~4 Off | `led1_off` / `led2_off` / `led3_off` / `led4_off` | 对应 LED 灭 |
| All On | `led_on` | 4 个 LED 全亮 |
| All Off | `led_off` | 4 个 LED 全灭 |
| Servo Turn (下拉角度) | `servo_0` / `servo_45` / `servo_90` / `servo_135` / `servo_180` | 舵机转对应角度 |
| Buzzer Beep | `buzzer_on` | 蜂鸣器(应用层 OK,驱动未装,LOG_W) |
| LCD 6 颜色 | `lcd_red` / `lcd_green` / `lcd_blue` / `lcd_white` / `lcd_black` / `lcd_yellow` | LCD 屏变对应颜色 |

收到 broker 转发的温湿度数据时,MainWindow 解析过程采用字符串查找 + 切片的简陋方式:用 `indexOf("\"hum\"")` 找 hum 字段起始位置,再找 `:` 和 `,` 提取数字,设置到 m_humiLabel 即可,温度字段同理。这种解析方式的好处是不依赖 Qt 的 JSON 模块(Qt 4.8 默认不编译进去),代码更轻;坏处是 payload 格式稍有变化就解析错,生产环境应该用 QJsonDocument 等正规 JSON 库。

### 6.3.3 设计权衡

本系统在 Controller 设计时也做了若干权衡。比如 Base Topic 设计为可改而非写死,是因为实际部署时可能有多台实验箱(改 `s5p6818` 为 `s5p6819` 等即可),无需改代码;启动后 300 毫秒自动连接 broker,无需用户手动点按钮,演示更流畅;命令字符串协议易调试(`mosquitto_pub -m "led_on"` 一行就能测),不需 JSON 解析。这些都是教学项目语境下的合理选择,如果是工业 IoT 网关,会换成 QtMqtt 库 + QJsonDocument + TLS 双向认证 + reconnect 策略。

## 6.4 本章小结

本章实现了 IoT 系统的第三个角色——**控制端软件 Controller**。它通过订阅 `s5p6818/#` 接收温湿度数据,通过发布到 `s5p6818/device/ctrl` 下发控制命令,与实验箱 `mqtt_iot` 完全解耦(双方只通过 broker 间接通信)。

技术上采用 Qt 4.8 + QProcess 调 `mosquitto_pub/sub` 的轻量方案,不依赖 libmosquitto C 库,让 Controller 在 Ubuntu 12.04 和 Windows 都能直接 `qmake && make` 跑通。UI 上通过左右分栏设计,左栏控制、右栏设备可视化(FarSightWidget + LCD 颜色叠加),用户能直观看到控制后的效果。

至此,本系统三方角色的软件实现全部完成:**实验箱 `mqtt_iot`**(第 4 章)+ **VM Mosquitto broker**(第 5 章)+ **Controller Qt GUI**(本章)。整个系统的通信基于 MQTT pub/sub 协议,任意一方都可独立替换或扩展——例如把 Controller 换成 Web 仪表盘(用 mqtt.js + websocket),或者把 broker 换成云平台(EMQX/HiveMQ),设备端 `mqtt_iot` 都无需修改。这种**协议层解耦**是本系统最具扩展性的地方。
